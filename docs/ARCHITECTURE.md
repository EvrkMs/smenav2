# Smena — техническая часть

Черновик от 2026-11-10. Бизнес-правила — в [PLAN.md](PLAN.md); здесь то, как они реализуются.
Пометка **[решить]** — место, где выбран вариант по умолчанию, но нужно подтверждение.

## 1. Состав

```
src/
  Smena.Core/          чистая логика без БД: расчёт смены, сборка проводок, правила
  Smena.Server/        ASP.NET Core: REST API, EF Core, авторизация, outbox, раздача веба
  Smena.Client/        WinForms + WebView2 — оболочка клиента на кассе
web/
  cashier/             React: интерфейс кассы (перенос старого reactapp)
  panel/               React: панель root
  miniapp/             React: MiniApp сотрудника (отдельное приложение)
tests/
  Smena.Core.Tests/    расчёты и проводки
  Smena.Server.Tests/  API на настоящем Postgres
deploy/                docker-compose, пример .env
docs/
```

- `Smena.Core` отделён, чтобы формулы смены и сборка проводок проверялись тестами без базы.
- Сервер один: API, панель и MiniApp раздаются одним процессом. PostgreSQL — отдельный контейнер.
- Клиент на кассе: интерфейс (`web/cashier`) собирается в `wwwroot/cashier` и раздаётся сервером по адресу `/cashier/`. Программа на кассе (`src/Smena.Client`) — окно WebView2: открывает этот адрес и до загрузки страницы передаёт ей токен устройства; дальше React ходит на сервер обычным `fetch`. Обновление интерфейса — это обновление сервера, программу переустанавливать не нужно. Мост C#↔JS из старой версии (`NativeApiBridge`) больше не нужен, proto-файлов нет.
- Вместо потока обновлений сейфа (SSE) интерфейс перечитывает сейф и сотрудников раз в 15 секунд и берёт новый баланс из ответа на каждую операцию.

## 2. База данных

Все суммы — `int`, рубли. Время — `timestamptz` в UTC; часовой пояс клуба — настройка.

Идентификаторы `uuid` — версии 7 (`Guid.CreateVersion7()`): начинаются с времени создания, поэтому новые строки дописываются в конец B-tree индекса, а не разбрасываются по нему, как у случайных v4. Заодно сортировка по id совпадает с порядком создания.

Справочники вместо enum в базе. Виды счетов, виды категорий, типы транзакций — отдельные таблицы (`id`, `code`, `name`), на которые ссылаются внешние ключи. Строки создаются миграцией. В коде им соответствует C#-enum с теми же id: логика ветвится по этим значениям, поэтому новое значение — это всегда миграция плюс код, из панели они не добавляются. База при этом не примет несуществующий вид, а в SQL видны названия.

### Учёт

**account_kinds** — виды счетов: id, code, name, side.
`side` — сторона для проверки баланса транзакции: `Asset` («где деньги»: Safe, Bank, Expense) или `Source` («чьи деньги»: Employee, Revenue, Opening).

**accounts** — счета

| Поле | Тип | Примечание |
|---|---|---|
| id | int | |
| kind_id | FK → account_kinds | |
| employee_id | uuid? | только для счёта сотрудника, уникально |
| name | text | |

Системные счета (все, кроме счетов сотрудников) создаются миграцией по одному. Счёт сотрудника создаётся вместе с сотрудником.

**categories** — категории

| Поле | Тип | Примечание |
|---|---|---|
| id | int | |
| kind_id | FK → category_kinds | SafeIncome, SafeExpense, BankIncome, BankExpense, Revenue, Expense, Employee |
| name | text | |
| code | text? | у системных: `shift`, `payroll`, `acquiring_fee`, `shortage`, `safe_surplus`, `fine`, `bonus`, `inventory`… |
| counter_account_id | int? | второй счёт проводки — для категорий сейфа и банка |
| counter_category_id | int? | категория на втором счёте (например, «Хозяйственные» в расходах) |
| is_archived | bool | вместо удаления |

Приходы и расходы сейфа — разные `kind`, то есть раздельные справочники в панели; физически таблица одна. Системные категории (`code` заполнен) нельзя переименовать в панели и нельзя архивировать.

Три уровня: операция → транзакции → проводки. Внешние ключи с `ON DELETE CASCADE` сверху вниз.

**operations** — операции

| Поле | Тип | Примечание |
|---|---|---|
| id | uuid | |
| type_id | FK → operation_types | ShiftClose, Payout, SafeIncome, SafeExpense, BankIncome, BankExpense, BankReceipt, Inventory, Fine, Bonus, Opening |
| occurred_at | timestamptz | |
| comment | text | |
| actor | enum + text | Cashier / Root / System и подпись |
| idempotency_key | uuid? | уникально; повтор запроса не создаёт дубль |
| cancelled_at, cancelled_by, cancel_reason | | отмена всей операции |

**transactions** — транзакции: одно движение одной суммы

| Поле | Тип | Примечание |
|---|---|---|
| id | uuid | |
| operation_id | FK → operations, CASCADE | |
| position | smallint | порядок внутри операции |
| amount | int, всегда > 0 (CHECK) | сумма хранится только здесь |
| note | text? | подпись строки внутри операции («Наличка в сейф», «ЗП: Иван») |

**entries** — проводки: запись в счёте

| Поле | Тип | Примечание |
|---|---|---|
| id | bigint | |
| transaction_id | FK → transactions, CASCADE | |
| account_id | FK → accounts | |
| direction | smallint: +1 или −1 (CHECK) | баланс этого счёта вырос или уменьшился |
| category_id | int? | |

Правила:

- Суммы, даты и комментария в проводке нет: сумма берётся из транзакции, дата и комментарий — из операции.
- Направление хранится в проводке и читается с точки зрения её счёта. У транзакции и операции направления нет.
- Баланс транзакции: сумма `direction` по проводкам на счетах стороны `Asset` равна сумме `direction` по счетам стороны `Source` (сумма у всех проводок транзакции одна). Проводок у транзакции всегда ровно две. Проверяется в коде при сборке и отложенным триггером в базе — чтобы ошибка в коде не могла записать несбалансированную транзакцию.
- В обычной работе ничего не изменяется и не удаляется: исправление — отмена операции и новая. Ручное удаление в базе остаётся возможным и безопасным за счёт каскада: удалённая операция или транзакция не оставляет хвостов в счетах.
- Смена, ожидаемое зачисление и подобные записи ссылаются на свою операцию тоже с каскадом — удаление операции закрытия смены удаляет и строку смены. Файлы фото на диске каскад не трогает: после ручного удаления смены они остаются сиротами.
- Баланс счёта = `SUM(transactions.amount × entries.direction)` по неотменённым операциям.
- В базе есть представление `account_movements`: проводка вместе с суммой, датой, комментарием, типом операции и признаком отмены. Балансы, отчёты и ручные запросы читают его, а не соединяют три таблицы каждый раз. Отдельного поля с балансом нет: объёмы маленькие, а расхождение кэша с журналом — лишний класс ошибок.
- Все операции, меняющие деньги, выполняются под одной общей блокировкой (`pg_advisory_xact_lock`). Касса одна, нагрузки нет; это убирает гонки без отдельных блокировок на каждый счёт.

### Ожидаемые зачисления в банк

Один механизм для эквайринга и инкассации.

Отдельных счетов «в пути» нет. Транзакция идёт сразу на счёт «Банк», а к ней прикреплена запись «ожидаемое зачисление» с условиями, ожидаемой суммой и подтверждением. Повторная транзакция «зачисление» не создаётся; при подтверждении появляется только транзакция расхода на комиссию.

Следствие: простая сумма проводок счёта «Банк» включает ещё не пришедшие деньги. Поэтому банк всегда показывается двумя числами:

- **в пути** = сумма `amount` неподтверждённых записей bank_receipts;
- **подтверждено** = баланс счёта по проводкам − «в пути».

Оба числа отдаёт представление `bank_balance`; напрямую сумму проводок банка никто не читает.

**receipt_channels** — каналы зачисления: id, code, name, delay_days?, fee_percent?.
Строки сейчас: «Терминал» (задержка и процент заданы) и «Инкассация» (без задержки и процента). Задержка и комиссия хранятся здесь, а не в общих настройках: когда выяснится, что у СБП свои условия, добавится строка «СБП» со своими значениями, без изменения схемы. Значения правит root в панели.

**bank_receipts** — ожидаемые зачисления

| Поле | Примечание |
|---|---|
| id | |
| transaction_id | FK → transactions, CASCADE, уникально — транзакция, которая положила деньги на «Банк» |
| channel_id | FK → receipt_channels |
| delay_days?, fee_percent? | снимок условий канала на момент создания |
| expected_at? | дата транзакции + задержка |
| expected_amount? | сумма транзакции − процент, считается по формуле при создании |
| confirmed_at? | пусто — деньги «в пути» |
| confirmed_amount? | сколько реально пришло, вводит root |
| fee_transaction_id? | транзакция расхода на комиссию, если была разница |

Сумма отправленного в записи не дублируется — она в транзакции.

Пример. Смена 10 ноября, безнал 12 000, у канала задержка 2 дня и комиссия 2 %:

| Когда | Что в базе | Что видно в панели |
|---|---|---|
| 10.11, закрытие смены | транзакция «Банк + / Выручка +» на 12 000; строка bank_receipts: delay_days 2, fee_percent 2, expected_at 12.11, expected_amount 11 760 | «В пути: 12 000» |
| 12.11 | ничего не меняется | «Ждёт подтверждения, ожидается 11 760» |
| root смотрит выписку, вводит 11 748 | одна транзакция «Банк − / Расходы:комиссия +» на 252; в bank_receipts заполнены confirmed_at, confirmed_amount 11 748, fee_transaction_id | «Зачислено 11 748, комиссия 252» |

`expected_amount` — только подсказка для формы подтверждения. В учёт идёт фактическая сумма, поэтому неточно известный процент ничего не ломает: реальная комиссия всегда равна разнице.

- Эквайринг: запись создаётся при закрытии смены, если безнал > 0. Условия канала копируются в запись: смена процента в канале старые записи не пересчитывает.
- Инкассация: запись создаётся транзакцией расхода сейфа с категорией «Инкассация». Ожидаемой даты и суммы нет.
- Состояние вычисляется, отдельного поля и фоновой задачи нет: не подтверждено и срок не настал — «в пути»; срок настал или его нет — «ждёт подтверждения»; есть `confirmed_at` — «зачислено».
- Подтверждение (root): вводится фактически зачисленная сумма. Если она меньше отправленной, создаётся операция BankReceipt с одной транзакцией «Банк − / Расходы:комиссия +» на разницу. Если равна — транзакции нет, только отметка в записи. Больше отправленной ввести нельзя.
- Транзакция комиссии принадлежит своей операции, а не исходной: исходная (закрытие смены) остаётся неизменной.
- Отмена исходной операции запрещена, пока зачисление подтверждено: сначала отменяется подтверждение.

### Сверка и корректировка банка

У сейфа расхождение находит админ при закрытии смены, и оно ложится на сотрудников. У банка так нельзя: списывать не на кого, а расходится он только когда что-то не внесли (забытый расход, плата банку за обслуживание).

- В панели есть «Сверка банка»: root вводит остаток из выписки, система показывает разницу с балансом счёта.
- Правильный способ убрать разницу — внести недостающие операции (расход или приход банка с категорией).
- Если причину найти не удалось — операция «Корректировка банка» с обязательным комментарием: Банк ± и Расходы или Выручка с системной категорией «Корректировка банка». Так подгонка видна в отчётах отдельной строкой, а не растворяется.
- Дата и введённый остаток каждой сверки сохраняются (**bank_reconciliations**: id, checked_at, statement_balance, ledger_balance, adjust_operation_id?).

### Фото

**photo_sessions**: id, token (уникален), created_at, closed_at?.
**photos**: id, session_id, shift_id?, sha256 (уникален), path, bytes, width, height, taken_at?, is_stale, uploaded_at.
**outbox_messages.photos_shift_id** — если задан, сообщение — альбом с фото этой смены, а текст — подпись к нему.

Фото расходов (чек к расходу из сейфа) пока нет; когда появятся, у сессии добавится назначение, у фото — ссылка на транзакцию.

Правило, на котором всё держится: фото открытой сессии ни к чему не привязаны, фото закрытой — привязаны к смене. Поэтому «стереть непривязанное» значит «удалить открытые сессии». Загрузка, закрытие смены и отмена сначала блокируют строку сессии (`SELECT … FOR UPDATE`), так что фото не может оказаться «между».

Порядок для смены:

1. Клиент создаёт сессию и показывает QR.
2. Админ загружает фото с телефона; они лежат в сессии как непривязанные. Клиент видит их число.
3. Клиент отправляет отчёт вместе с id сессии. Сервер привязывает фото к смене в той же транзакции БД, что и закрытие: либо смена закрыта вместе с фото, либо не записано ничего.
4. Сессия закрывается.

- Если сервер отклонил отчёт (ошибка в цифрах), сессия остаётся открытой: админ исправляет и отправляет снова, фото переснимать не нужно.
- Если отчёт так и не отправлен, непривязанные фото удаляются с диска и из базы в двух случаях: админ нажал «Отменить» или создана новая сессия. Касса одна, поэтому активная сессия всегда одна, и создание новой стирает всё непривязанное от прежних. Таймера и фоновой очистки нет. Хеши удалённых фото не мешают загрузить те же снимки заново.
- Фото обязательны: экран LanGame, экран «МойСклад» и чек сверки итогов с терминала. Сервер не закрывает смену, если фото меньше минимума (настройка, по умолчанию 3). Сверх минимума можно приложить ещё — например, калькулятор подсчёта кассы. Что изображено на снимке, система не проверяет, только количество.
- Отмена уже закрытой смены root'ом фото не удаляет: они остаются при отменённой смене.
- Файлы — на диске (`Photos:StoragePath`, по каталогу на месяц), в базе только путь. При развёртывании в контейнере это должен быть том.
- Приём: посчитать хеш оригинала → отказать, если такой уже есть → определить формат по первым байтам (JPEG, PNG, WebP, HEIC; остальное отклоняется) → прочитать время съёмки → повернуть по метке ориентации → пережать в JPEG (длинная сторона 1600 px, качество 80, без метаданных) → сохранить. Маленькие снимки не растягиваются.
- Обработка — Magick.NET (Apache 2.0). ImageSharp не подошёл: версии с 3.2 требуют платный ключ лицензии при сборке, а в 3.1 остались незакрытые уязвимости. Библиотеке передаётся только файл, формат которого сервер определил сам: сама она читает десятки форматов, в том числе небезопасных.
- Ограничения: файл до 25 МБ, до 120 Мп, до 10 фото в сессии (столько вмещает один альбом Telegram). Снимки обрабатываются по одному.
- `is_stale` = снимок старше лимита (настройка, 5 ч) или времени в метаданных нет. Время без часового пояса считается временем клуба; если пояс в файле есть — берётся он.
- В Telegram после текста отчёта уходит одно сообщение-альбом с подписью; в тексте отчёта — число фото и число сомнительных.
- Адрес в QR: `Photos:PublicBaseUrl`, а если не задан — адрес, по которому к серверу обратилась касса. Телефон должен видеть сервер по этому адресу.
- Страница загрузки — один статический файл `wwwroot/upload/index.html` без сборки: показывает счётчик, снимки и позволяет удалить неудачный.

### Служебное

**outbox_messages**: id, kind, payload (jsonb), status, attempts, next_attempt_at, telegram_message_id, created_at.
**club_settings** — настройки клуба: одна строка с типизированными колонками и ограничениями базы (размен, максимум сотрудников и часов, минимум фото, лимит давности фото, часовой пояс), а не таблица «ключ — значение». Часовой пояс — настройка клуба, меняется root в панели (по умолчанию `Europe/Moscow`); переменной среды для него нет. Несуществующий пояс база не принимает. Новые настройки (чаты и темы Telegram и т. п.) добавляются колонками на своём этапе. Задержка и комиссия эквайринга живут в receipt_channels.
**Авторизация root** — таблицы ASP.NET Core Identity.
**devices**: id, name, token_hash — устройства кассы.

## 3. Закрытие смены

`Smena.Core` получает ввод, ставки сотрудников, баланс сейфа и настройки; возвращает либо ошибку, либо расчёт и список проводок. Сервер только читает данные, вызывает расчёт и сохраняет.

Порядок на сервере, в одной транзакции БД:

1. Общая блокировка.
2. Проверка `idempotency_key`: если транзакция с таким ключом есть — вернуть её результат.
3. Чтение баланса сейфа и ставок.
4. Расчёт в `Smena.Core`; при ошибке — откат и ответ с причиной.
5. Запись operation, её transactions и entries, shift, shift_employees, bank_receipt (если есть безнал).
6. Привязка фото из сессии к смене (фото загружены до отправки отчёта).
7. Сообщения в outbox.
8. Коммит.

Клиент не дублирует формулы: предпросмотр он получает от сервера (`POST /api/shifts/calc`) — тот же расчёт без записи. В старой версии формулы жили в двух местах и расходились.

## 4. Отмена

- Только root в панели, с обязательной причиной.
- Отмена ставит `cancelled_at` на операцию; балансы меняются сами.
- В outbox уходит сообщение «отменено» ответом на исходное; старое сообщение не удаляется.
- Отменить можно только последнюю смену. Расхождение сейфа в каждой смене считается от баланса на тот момент; отмена смены из середины задним числом делает «уравнивания» всех следующих смен неверными. Старую ошибку исправляют корректирующей транзакцией.
- Смену с уже подтверждённым зачислением эквайринга отменить нельзя, пока не отменено зачисление.
- Остальные операции (выплата, расход, штраф…) отменяются в любом порядке.

## 5. Авторизация

| Кто | Способ |
|---|---|
| Касса | токен устройства в заголовке; выдаётся в панели |
| Root | ASP.NET Core Identity, cookie |
| Сотрудник (MiniApp) | заголовок `Authorization: tma <initData>`; на каждом запросе сервер проверяет подпись Telegram (HMAC токеном бота, срок 24 ч) и ищет активного сотрудника по telegram_id. Сессий сервер не хранит: проверка — один HMAC, а отключённый сотрудник теряет доступ сразу |
| Страница загрузки фото | одноразовый токен сессии в ссылке из QR |

## 6. API

Префикс `/api`. Ошибки бизнес-правил — `422` с текстом для показа пользователю.

**Касса** (токен устройства)

| Метод | Назначение |
|---|---|
| GET /config | лимиты и размен |
| GET /employees | активные сотрудники с балансами |
| GET /safe | баланс сейфа |
| GET /safe/stream | обновления баланса (SSE) |
| POST /shifts/calc | предпросмотр расчёта |
| POST /shifts | закрыть смену |
| POST /payouts | аванс/ЗП из сейфа |
| GET /categories?kind= | категории сейфа |
| POST /safe/income, /safe/expense | приход и расход сейфа |
| POST /photo-sessions, GET /photo-sessions/{id}, DELETE /photo-sessions/{id} | создать сессию (ссылка для QR), узнать число загруженных фото, сбросить фото |
| GET /stock, POST /stock/refresh | остатки «МойСклад» для пересчёта из памяти сервера; перечитать их сейчас |

**Загрузка фото** (секрет сессии в ссылке): `GET /u/{token}` — страница; `GET /api/upload/{token}` — состояние; `POST /api/upload/{token}` — файл телом запроса; `GET` и `DELETE /api/upload/{token}/photos/{id}` — посмотреть и убрать снимок. Панель берёт снимки смены по `GET /api/root/photos/{id}`.

**Панель** (`/api/root`, cookie)

- смены: список, карточка, отмена;
- операции: список с фильтрами, карточка с транзакциями и проводками, отмена;
- счета: балансы; банк — приход и расход;
- сотрудники: создание, правка, отключение; выплата (сейф, банк, сверх баланса); штраф, премия;
- инвентаризация;
- зачисления в банк (эквайринг и инкассация): список, подтверждение с фактической суммой;
- категории: создание, правка, архив;
- стартовые остатки;
- отчёты (позже): P&L по категориям выручки и расходов, ДДС по категориям сейфа и банка, выручка по программам — все читают `account_movements`;
- устройства кассы, настройки.

**MiniApp** (`/api/me`): `GET /api/me` — имя, ставка, баланс; `GET /api/me/operations?take=&before=` — история движений по счёту сотрудника от новых к старым, без отменённых операций. Идентификатор сотрудника в запросах не передаётся — он берётся только из подписи Telegram. При входе обновляется `employees.telegram_username`.

Интерфейс (`web/miniapp`, адрес `/miniapp/`) не подключает скрипт `telegram-web-app.js`: он грузится с telegram.org, который может быть недоступен. Строку `initData` и цвета темы Telegram передаёт во фрагменте адреса страницы (`#tgWebAppData=…&tgWebAppThemeParams=…`), оттуда страница их и берёт.

## 7. Telegram

- Бизнес-операция только кладёт сообщение в `outbox_messages` в своей транзакции БД.
- Фоновый отправитель шлёт по очереди, с повторами и растущей паузой; после N неудач помечает сообщение и показывает его в панели.
- Недоступность Telegram не мешает закрыть смену.
- Фото уходят в Telegram тем же способом, после текста отчёта.
- Бот также открывает MiniApp.

## 8. Этапы

Каждый этап заканчивается работающим и проверенным результатом.

1. **Каркас.** Решение, docker-compose с Postgres, миграции, настройки, проверка здоровья.
2. **Учёт.** Счета, справочники, операции, транзакции, проводки, баланс, отмена, триггеры баланса, сотрудники со счетами. Тесты. Системные категории заводятся миграциями на тех этапах, где появляются использующие их операции.
3. **Смена.** Расчёт в `Smena.Core` с тестами на все правила из PLAN.md; `/shifts/calc` и `/shifts`.
4. **Операции кассы.** Выплаты, приход и расход сейфа с категориями, эквайринг в пути.
5. **Клиент на кассе.** Перенос интерфейса, переход на REST, раздельный ввод программ. Фото пока без загрузки.
6. **Outbox и Telegram.** Сообщения по сменам, сейфу, ЗП.
7. **Панель.** Вход, смены, транзакции, отмена, сотрудники, штрафы и премии, инвентаризация, банк, подтверждение эквайринга, категории, стартовые остатки, отчёты.
8. **Фото.** QR, страница загрузки, обработка, показ в панели, отправка в Telegram.
9. **MiniApp.** Вход по подписи Telegram, баланс и история сотрудника.
10. **Пересчёт склада.** Перенос сводки по «МойСклад». Сервер читает отчёт «Остатки» и ассортимент, сопоставляет их по идентификатору товара (а если его нет — по названию с артикулом) и держит результат в памяти: касса получает остатки мгновенно и не зависит от того, отвечает ли «МойСклад» сейчас. Сбой обновления не стирает прежние остатки. Сравнение с фактом делает касса; сводка на сервер не отправляется — это появится вместе с применением разницы.
11. **Переход.** Ввод стартовых остатков, неделя параллельной работы со старой версией, отключение старой.
