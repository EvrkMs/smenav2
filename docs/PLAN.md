# Smena — план новой версии

Черновик от 2026-11-10. Здесь только то, что согласовано в обсуждении; нерешённое — в разделе «Открытые вопросы».
Старый код для справки: [Smena](https://github.com/EvrkMs/Smena), [Smena.Client](https://github.com/EvrkMs/Smena.Client). Его не правим, пишем заново.

## 1. Назначение и границы

Инструмент закрытия смены администратором ПК-клуба и учёта денег вокруг этого: сейф, безнал, ЗП сотрудников, расходы.

- Один клуб, одна касса. Для своего пользования, не продукт.
- Программы клуба: «МойСклад» (товары) и LanGame (аккаунты клиентов, мониторинг ПК). Терминал — отдельный фискальный аппарат, к программам не подключён.
- Программа — помощник, а не система защиты: без PIN-кодов и антифрода.
- Ролей сотрудников нет. Передача кассы внутри смены не отслеживается.

## 2. Кто и через что работает

| Кто | Интерфейс | Что может |
|---|---|---|
| Администратор смены | клиент на кассе | закрыть смену, аванс/ЗП из сейфа, расход из сейфа, приход в сейф |
| Root (владелец системы) | веб-панель | всё, включая отмену транзакций и закрытых смен, расходы и выплаты с банка, подтверждение зачислений эквайринга, сотрудников |
| Сотрудник | Telegram MiniApp | личный кабинет: баланс ЗП и история |

- При добавлении сотрудника обязателен Telegram ID; остальное (имя и т. п.) подтягивается при первом входе в MiniApp.
- Telegram-чаты остаются для админов, но перестают быть обязательными: всё видно на сайте. Отправка сообщений — через outbox (запись в БД в той же транзакции, отдельный отправитель с повторами), а не внутри бизнес-операции.

## 3. Модель учёта

Двойная запись.

Три уровня:

- **Операция** — что произошло с точки зрения человека: закрытие смены, аванс, расход, инкассация. Дата/время, тип, комментарий, автор, флаг отмены. Операция состоит из одной или нескольких транзакций: аванс — одна, закрытие смены — несколько (наличка в сейф, безнал, начисление ЗП каждому, минусы…).
- **Транзакция** — одно движение одной суммы, объединяющее счета. Сумма (всегда положительная) хранится здесь, один раз.
- **Проводка** — запись в счёте: какой счёт и в какую сторону («+» или «−») его меняет эта транзакция, плюс категория. Суммы, даты и комментария в проводке нет — они берутся из транзакции и операции.
- Удаление каскадное: удалил операцию — исчезли её транзакции и их проводки; удалил транзакцию — исчезли её проводки. Это нужно и для ручной чистки в базе.
- Направление принадлежит проводке, а не транзакции, и читается с точки зрения самого счёта: «+» — баланс этого счёта вырос, «−» — уменьшился. В одной транзакции у разных счетов направления разные: при инкассации сейф «−», а банк «+»; при авансе и сейф «−», и баланс сотрудника «−».
- Баланс счёта = сумма его «+» минус сумма его «−» по неотменённым операциям. Знак на экране не переворачивается: баланс сотрудника 5000 — клуб должен ему 5000; −3000 — сотрудник в минусе.
- Проверка транзакции: счета делятся на две стороны (см. таблицу). Изменение по стороне «где деньги» должно равняться изменению по стороне «чьи деньги». Это та же двойная запись, только без бухгалтерских «дебет/кредит».
- Все суммы — целые рубли (int), копейки не учитываются.
- **Отмена** — флаг на всей операции; отдельную транзакцию или проводку в панели отменить нельзя. Отмена — только root через панель.
- История не схлопывается (старая компакция журналов не нужна).

### Счета

| Счёт | Сторона | Смысл баланса |
|---|---|---|
| Сейф | где деньги | наличка в сейфе |
| Банк | где деньги | деньги на расчётном счёте; показывается двумя числами — «подтверждено» и «в пути» |
| Расходы | где деньги | на что потрачено; категории: ФОТ, комиссии, хозяйственные и т. д. |
| Сотрудник (на каждого свой) | чьи деньги | сколько клуб должен сотруднику |
| Выручка | чьи деньги | заработано; категории: смена, излишек сейфа, удержание, штрафы |
| Стартовые остатки | чьи деньги | с чем начали учёт |

- Категории строго свои у каждого вида счёта.
- Касса (1000 ₽ на размен) счётом не является — она постоянна.
- Счёт «Банк» ведётся честно: все движения по расчётному счёту вносятся в панели (раздел расходов).

### Операции

| Операция | Проводки |
|---|---|
| Смена: наличка | Сейф + (факт нал − 1000) / Выручка + |
| Смена: безнал | Банк + / Выручка + (с записью «ждёт подтверждения») |
| Смена: начисление ЗП | Расходы:ФОТ + / Сотрудник + (ставка × часы) |
| Смена: недостача кассы | Сотрудник − / Выручка:удержание + |
| Смена: недостача сейфа | Сейф − / Сотрудник − |
| Смена: излишек сейфа | Сейф + / Выручка:излишек + |
| Аванс, выплата ЗП из сейфа | Сейф − / Сотрудник − |
| Выплата ЗП с банка (root) | Банк − / Сотрудник − |
| Расход из сейфа | Сейф − / Расходы + |
| Расход с банка (root) | Банк − / Расходы + |
| Приход в сейф «Снято с банка» | Банк − / Сейф + |
| Инкассация (из сейфа в банк) | Сейф − / Банк + (с записью «ждёт подтверждения») |
| Подтверждение зачисления (root) | Банк − / Расходы:комиссия + на разницу между отправленным и пришедшим; разницы нет — транзакции нет |
| Инвентаризация товара (root) | Сотрудник − / Выручка:удержание +; сумма увеличивается до делящейся на число сотрудников без остатка, доли одинаковые (1000 на троих → по 334) |
| Штраф (root) | Сотрудник − / Выручка:штрафы + |
| Премия (root) | Расходы:ФОТ + / Сотрудник + |
| Ввод стартовых остатков (root) | нужный счёт / Стартовые остатки |

Каждая строка таблицы с одной суммой — одна транзакция. Закрытие смены — одна операция, в которой все строки «Смена: …» идут отдельными транзакциями.

### Категории сейфа

- Категории приходов сейфа и расходов сейфа — два отдельных справочника (своя таблица), редактируются root в панели.
- Примеры: приход «Снято с банка»; расход «Инкассация» (наличка уходит в банк), «Хозяйственные».
- У категории задан второй счёт проводки. «Снято с банка» → Банк, «Инкассация» → Банк, «Хозяйственные» → Расходы. Админ выбирает только категорию, транзакция сама получается сбалансированной.
- Инкассация считается «в пути», пока root не подтвердит зачисление в панели. При подтверждении указывается фактически зачисленная сумма; разница уходит в расходы как комиссия. Механизм тот же, что у эквайринга (раздел 5).

## 4. Закрытие смены

Ввод: факт нал, факт безнал, программные значения, факт сейфа, причина недостачи, до 3 сотрудников (часы, минус).

- Программные значения вводятся раздельно по программам: «МойСклад» нал/безнал и LanGame нал/безнал. Складывает система, а не админ; разбивка сохраняется, чтобы видеть, откуда сколько пришло.
- Стартовая 1000 есть и в факте, и в программе (числится в LanGame, нал), поэтому на расхождение не влияет; из факта она вычитается только при расчёте выручки.
- Выручка = факт нал − 1000 + факт безнал. Итог = выручка − ЗП смены.
- Расхождение кассы — одной суммой: (факт нал + факт безнал) − (склад нал + склад безнал + LanGame нал + LanGame безнал). Так задумано: админ может пробить не тот тип оплаты. Расхождение не привязывается ни к типу оплаты, ни к программе — касса одна, и откуда взялся минус, определить нельзя.
- Расхождение сейфа = факт сейфа − баланс счёта «Сейф». Сейф считают **до** того, как положили выручку смены.
- Вся наличка сверх 1000 всегда уходит в сейф.
- Требуемый минус = недостача кассы + недостача сейфа. Излишки недостачу не гасят. Излишек кассы остаётся в выручке, излишек сейфа — отдельная строка.
- Расходы наличкой из кассы в течение смены отдельно не учитываются — попадают в недостачу.
- Минус делят между собой вручную (подмены, пересчёт кассы при передаче); сумма долей должна совпасть с требуемым минусом. Клиент показывает требуемую сумму — в арифметике ошибались.
- Доля минуса сотрудника ≤ его ЗП за эту смену (ставка × часы). Если общий минус больше ЗП смены — смена не закрывается; обходного пути нет и намёков на него в интерфейсе нет.
- Ограничения: максимум 3 сотрудника, суммарно ≤ 12 часов. 0 часов допустимо.
- Причина недостачи обязательна при любой недостаче — и кассы, и сейфа.
- Если в кассе меньше размена (факт нал < 1000), недостающее до размена берётся из сейфа: сейф уменьшается, наличная часть выручки отрицательная. Так же работала старая версия.
- «Итог» отчёта (выручка − ЗП к выплате) и прибыль по счетам (выручка − расходы) отличаются на недостачу сейфа: удержание за неё уменьшает ЗП к выплате, но в выручку не идёт — оно возмещает деньги, пропавшие из сейфа. Удержание за недостачу кассы в выручку идёт, и там обе цифры совпадают.

## 5. Эквайринг

- Отдельных счетов «в пути» нет. Транзакция безнала при закрытии смены идёт сразу на счёт «Банк», а к ней прикреплена запись ожидаемого зачисления.
- В записи сохраняются условия на момент создания (задержка и процент комиссии — чтобы их последующее изменение не затронуло старые записи), ожидаемая дата и ожидаемая сумма по формуле. Ручного ввода здесь нет.
- Пока запись не подтверждена, её сумма показывается как «в пути» и в «подтверждённый» остаток банка не входит.
- Root подтверждает и вводит, сколько реально пришло. Создаётся только одна транзакция — расход на комиссию (Банк − / Расходы:комиссия +) на разницу. Повторной транзакции «зачисление» нет.
- Зачисление ведётся по каждой смене отдельно (если банк платит иначе — поправим).
- СБП пока не выделяется: безнал — одна общая сумма. Задержка и процент комиссии заданы у канала зачисления («Терминал»), а не глобально: когда условия СБП станут понятны, добавится свой канал.
- В учёт идёт фактическая сумма; расчётный процент — лишь подсказка, поэтому неточно известная комиссия ничего не ломает.
- Настоящие условия терминала пока неизвестны: в базе стоит задержка 1 день и комиссия 0 %. Их нужно заменить на реальные (таблица `receipt_channels`; позже — в панели).
- Желаемое на будущее: получать суммы из 1С по API. Сейчас недоступно.
- Расхождение банка с выпиской убирается внесением недостающих операций, в крайнем случае — операцией «Корректировка банка» с обязательным комментарием. На сотрудников оно не ложится.

## 6. Выплаты

- Администратор платит аванс/ЗП только из сейфа и не больше текущего баланса сотрудника.
- Выплаты с банка и принудительные выплаты — только root в панели.
- Через панель сотруднику можно выдать больше, чем он заработал: баланс уходит в минус. Отдельной операции и отдельного названия для долга нет — баланс просто показывается как «−N» и гасится следующими начислениями сам.
- Штрафы и премии выписывает только root в панели; администраторы не могут.
- Администратор не может выдать или потратить из сейфа больше, чем в нём числится по учёту: сейф в минус с кассы не уходит.
- Расход из сейфа на категорию расходов (например, «Хозяйственные») требует комментарий; инкассация и снятие с банка — нет.
- Начальный набор категорий сейфа для администратора: приход — «Снято с банка», «Прочий приход»; расход — «Инкассация», «Хозяйственные». Остальные root заведёт в панели.

## 6а. Отчёты (на будущее, модель под них готова)

- **P&L (прибыли и убытки)** — строится только по счетам «Выручка» и «Расходы» с их категориями за период. Прибыль = выручка − расходы.
  - ЗП попадает в расходы в момент начисления (закрытие смены), а не выплаты. Выплата ЗП, инкассация, снятие с банка, стартовые остатки в P&L не участвуют — это перемещения денег, а не доход или расход.
  - Комиссии банка — отдельная категория расходов, поэтому каждая комиссия проводится своей транзакцией.
  - Недостача кассы, удержанная с сотрудника, идёт отдельной строкой выручки «Удержание». Фактическая выручка смены + удержание = сумма по программам, то есть после удержания выручка всегда сходится с LanGame и «МойСклад» (при излишке — превышает их).
- **ДДС (движение денег)** — строится по счетам «Сейф» и «Банк» с их категориями: сколько пришло и ушло и по каким причинам. Здесь выплаты ЗП и инкассации видны.
- Для этого категории и заведены отдельно у каждого вида счёта: категории выручки и расходов отвечают за P&L, категории сейфа и банка — за ДДС.

## 7. Стек

- Сервер: ASP.NET Core + EF Core + PostgreSQL.
- Клиент на кассе: WinForms + WebView2 с React. Интерфейс старого Smena.Client переносится как есть (он удачный), меняется транспорт: REST вместо gRPC.
- Панель root и MiniApp сотрудника: веб на React.
- Telegram: бот для уведомлений через outbox и вход в MiniApp.

## 8. Фото

Запроса фото через бота больше нет. Клиент показывает QR со ссылкой на страницу загрузки, админ снимает с телефона. Сделано на этапе 8; устройство — в ARCHITECTURE.md, раздел «Фото».

- фото обязательны: не меньше трёх (экран LanGame, экран «МойСклад», чек сверки итогов терминала), не больше десяти; без них смена не закрывается;
- фото загружаются до отправки отчёта и привязываются к смене в момент закрытия;
- неотправленные фото стираются кнопкой «Сбросить фото» или при показе нового QR;
- повтор того же файла отсекается по хешу (цель — именно повторная отправка той же фотографии, не похожего кадра);
- сервер пережимает снимок в уменьшенный JPEG — метаданные пропадают, размер падает;
- блочная дедупликация не подходит: JPEG уже сжат, у разных снимков одинаковых блоков байт не бывает;
- время съёмки читается из метаданных до пережатия; если снимок старше 5 часов или времени нет — фото принимается, но в отчёте ставится отметка;
- фото хранятся на сервере и после отправки в Telegram не удаляются: при 3–4 фото за смену (две смены в сутки) это по оценке меньше гигабайта в год. Если реальный объём окажется больше — вернуться к вопросу.

## 9. Открытые вопросы

1. Отменить можно только последнюю смену (решено); прочие транзакции — в любом порядке.
2. Пересчёт склада по «МойСклад» переносится как есть (сводка расхождений). Позже — отправка и применение разницы как списания или оприходования.
3. СБП: своя комиссия и задержка — отложено.
4. Автоматическое получение банковских сумм (на будущее, не в первой версии): из 1С, если там включён доступ по OData или HTTP-сервис, либо напрямую из API банка. Цель — подставлять фактическую сумму зачисления и остаток для сверки, подтверждение всё равно остаётся за root. Нужно выяснить: какая конфигурация 1С, локальная или облачная, кто её администрирует, какой банк.
